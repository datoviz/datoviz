## Release Candidate Posture

RC1 is a controlled public testing milestone for the v0.4 refactor. The goal is useful technical
feedback before the final v0.4 release, not maximum visibility.

Use this framing in public notes:

- Datoviz v0.4.0rc1 is the first release candidate of a major C-first Vulkan refactor.
- It is intended for early technical testing of installation, examples, platform behavior, docs, and
  API boundaries.
- It is not the final v0.4 release.
- It is not VisPy 2.0 and should not be presented as a production-ready high-level plotting library.
- WebGPU/WASM, compute+graphics, and Qt/PyQt hosted rendering are scoped early surfaces, not broad
  parity promises.


## Scope

Datoviz v0.4 is a C-first rewrite of the rendering engine. RC1 is the API and architecture
candidate: it is intended for early testers of the scene/app runtime, raw Python bindings, packaging
route, and experimental browser/provider slices.

Release-facing surfaces:

- native scene/app path: scene, figure, panel, retained visuals, controllers, app/offscreen, capture;
- public C headers and installed CMake/pkg-config consumer metadata;
- raw generated Python `ctypes` binding;
- release example set and generated C reference outline;
- WebGPU/WASM experimental subset for promoted live examples;
- compute+graphics experimental slice;
- Qt/PyQt hosted rendering through the optional `datoviz_qtbridge` provider.

Not part of v0.4:

- v0.3 source or ABI compatibility;
- the old object-oriented Python plotting API;
- high-level statistical plotting, notebook/dashboard/napari workflows, and publication vector
  export, which belong above Datoviz in GSP/VisPy2/Matplotlib;
- full WebGPU parity with native Vulkan;
- a general compute framework.


## Who Should Test RC1

RC1 is most useful for:

- C and C++ users who can evaluate the scene/app API, ownership rules, and installed headers;
- Python users willing to test low-level bindings rather than a high-level plotting API;
- contributors testing Linux, macOS, Windows, Vulkan drivers, and wheel installation;
- graphics and WebGPU developers who can report backend capability gaps with concrete diagnostics;
- existing Datoviz users checking which v0.3 visible capabilities are fixed, experimental, deferred,
  or external/GSP-owned.

The preferred RC1 outcome is a small number of serious external reports: installation failures,
driver/platform bugs, broken examples, unclear API boundaries, and reproducible rendering issues.

## Known Issues And Limitations

- Wheel CI is green for Linux x86_64/aarch64, macOS 15 arm64/Intel, and Windows AMD64/ARM64;
  final public artifact upload and source-bundle checksum are still pending.
- Explicit linear `f16`/`f32` scientific image export/readback is deferred beyond RC1; v0.4.0
  capture is sRGB RGBA8.
- WebGPU/WASM supports the promoted example subset only; unsupported features should report clear
  diagnostics rather than silently diverging from native scene semantics.
- Compute+graphics is experimental and should not be treated as a general compute framework.
- Qt/PyQt hosting requires the optional `datoviz_qtbridge` provider, compatible Qt/PyQt Vulkan
  bindings, and platform WSI support. The base wheel must still install and import without Qt.
- The system PyQt6 package on the current Linux validation host lacks `QVulkanInstance`; valid PyQt
  proof used an isolated PyQt6 wheel.
- v0.4 does not preserve v0.3 source or ABI compatibility.


## Migration Notes

For v0.3 users:

- Rewrite code against the v0.4 C scene/app API or the generated raw Python `ctypes` layer.
- Do not expect old Python object-oriented plotting names to exist in Datoviz v0.4.
- Use GSP/VisPy2 for high-level Python plotting workflows as that layer becomes available.
- Treat Datoviz as the interactive GPU backend and raster capture backend, not the publication
  PDF/SVG/vector export layer.


## Feedback Requested

For RC1, feedback is most useful on:

- installability of wheels and source bundles on clean machines;
- CMake consumer behavior from installed wheels and system installs;
- public C header usability and ownership/lifetime clarity;
- raw `ctypes` binding import and basic scene construction;
- visible gaps in the v0.3 parity table;
- WebGPU diagnostics for unsupported browser paths;
- Qt/PyQt provider diagnostics on machines with different Qt/PyQt packages.

Report issues with the matching GitHub issue form when possible. Include OS, GPU, driver version,
Python version, installation method, Datoviz version or commit, the smallest reproducer, and a
screenshot or terminal output for rendering and installation failures.
