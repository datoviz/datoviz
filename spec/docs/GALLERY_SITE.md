# Gallery Site Notes

This document owns public-doc-site implementation notes for the v0.4 gallery. Scene example style
rules live in [`../scene/examples/STYLE.md`](../scene/examples/STYLE.md).


## MkDocs Material Direction

For v0.4, keep the public website and documentation in one MkDocs Material site. The goal is not a
separate marketing stack; it is a visual documentation front door backed by reproducible gallery
assets. A custom web application becomes useful later only if Datoviz needs live WebGPU embeds,
benchmark dashboards, richer release/news pages, or product-level storytelling that MkDocs cannot
carry cleanly.

Use this order of complexity:

1. Markdown plus Material cards for most index pages.
2. Custom CSS in `docs/stylesheets/extra.css` for Datoviz-specific card grids, image overlays, dark
   gallery bands, responsive media, badges, and lead cards.
3. Generated Markdown for gallery pages from example metadata.
4. A page-local template override only for the homepage or top gallery index if Markdown becomes
   too constrained.
5. Additional JavaScript only for progressive enhancement such as lightweight filters,
   media lazy-loading, or WebGPU demo mounting.

Do not fork the Material theme for normal gallery work. Prefer small CSS and template overrides that
can survive theme upgrades.

| Showcase page | one large screenshot or looped video, short thesis, source link, run/capture command, feature tags |
| Visual-family page | controlled baseline image, supported attributes, minimal C example, deferred variants |
| Technique page | before/after or side-by-side image pair, limits, backend requirements |
| Runtime/WebGPU page | explicit experimental labels, supported subset, unsupported-feature diagnostics |

Example cards should use real `<img>` or `<video>` elements, not CSS background images, so alt text,
loading behavior, social previews, and future asset checks stay straightforward.


## Live WebGPU/WASM Examples

Treat live WebGPU/WASM gallery examples as progressive enhancement over stable PNG or video
artifacts. The default gallery artifact remains static media; live execution is an optional browser
path for examples where interactivity, animation, or backend proof materially improves the page.

The source of truth remains the normal C example tree plus example metadata. WASM modules,
JavaScript bundles, packed assets, generated manifests, and deployment-specific paths are generated
artifacts. Do not commit them unless a release-artifact policy explicitly approves the exact files.

Each gallery example may advertise independent capabilities:

| Capability | Meaning |
| --- | --- |
| `static-media` | Has PNG and/or video fallback used as the default gallery artifact. |
| `wasm-supported` | Builds and runs through the portable WASM/WebGPU scene path. |
| `gallery-live` | Is selected for public live embedding with browser fallback UX. |

Live embeds must:

1. load only after user intent or viewport visibility;
2. fall back to PNG or video when WebGPU, WASM, assets, or diagnostics fail;
3. use the shared scene -> DRP2 -> WebGPU path, not a duplicate gallery renderer;
4. be generated by CI/deployment from source examples and metadata;
5. report unsupported features honestly.

Data-backed live embeds must use fetched, versioned web bundles instead of growing the base WASM
module with build-time preloaded example data. The bundle contract and migration plan live in
[`../data/WEBGPU_DATA_BUNDLES.md`](../data/WEBGPU_DATA_BUNDLES.md).

Prefer broad WASM build coverage but curated public embedding. A release can compile many examples
to WASM for validation while showing only a small `gallery-live` subset on the public gallery.

## Homepage Media Profiles

Homepage presentation is a derivative of the existing gallery capture pipeline, selected explicitly from `media.profiles.homepage`. Default gallery capture semantics and assets are unchanged. Resolve the selected profile once into an effective capture descriptor; capture, encoding and validation consume that descriptor. Profile output and cache namespaces must not collide with the default gallery or other profiles, and unrelated editorial or unused-profile edits must not invalidate a selected capture.

Output playback time, scientific data time and presentation motion are distinct. Presentation overrides may hold a fixed pose or follow a bounded periodic sway, preserving the scenario's existing axes, pivots and registered layers. They must not rescale activity interpolation, simulation time or orbital time. A periodic presentation path must match pose and velocity at its loop boundary without duplicating the endpoint; data periodicity is validated independently. Existing default presentation behavior is retained without an override.

The homepage retains muted preview playback and explicit pause controls. Loading near the viewport does not authorize offscreen playback; previews pause when outside the viewport or the document is hidden, preserve a user's pause decision, and remain static for reduced motion or data-saving preferences. Video failure or absent JavaScript leaves a useful poster and example link.

Candidate generation, source commits and local review are separate from binary publication. Review evidence records exact asset hashes, source and renderer identity, selected settings, scientific timing checks and loop limitations. Only the exact manually approved assets may be published to approved destinations.

### Selected snapshot and codec delivery

The example manifest declares `homepage_media.selection`, a repository-relative JSON snapshot containing the exact selected video/poster names, byte counts and full SHA-256 identities. Normal homepage hydration verifies and copies that snapshot; it must not silently regenerate accepted assets. Candidate production remains an explicit separate operation with recorded encoder identities and settings. Missing or changed snapshot files fail publication preparation; hermetic builds remain independent of those binary files.

The selected point cloud and planet use AV1 first and H.264 High/3.1 compatibility fallbacks. Browser loading considers supported and locally available sources while preserving pause, visibility and reduced-motion behavior. Both streams represent the same six-million-point scene and approved camera path at 1280×720, 30 FPS and 9.6 seconds. The planet uses the approved 1,960,895-byte AV1 at 1280×720, 30 FPS and 14.4 seconds. Its fixed-quality H.264 fallback shares the same uncompressed source. Protein, point-cloud assets and cortex remain byte-for-byte unchanged.

The RC3 selection uses existing website hosting with local media URLs. It does not require creating an asset repository, migrating datasets or removing the data submodule. Homepage videos/posters are included in the website output and require exact final approval before committing or uploading binaries.

An optional later publication mode can set `DATOVIZ_HOMEPAGE_ASSET_BASE_URL` to the selected immutable HTTPS release origin. In that mode only the homepage media URLs are rewritten, and the homepage binary subtree is excluded from website Git output. Private/local builds retain local staged media. The selected snapshot is verified before deterministic package construction; source selection and package construction grant no network-publication authority. The explicit final user approval and publication guard remain required.
